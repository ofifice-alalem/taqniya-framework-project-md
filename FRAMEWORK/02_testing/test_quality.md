# Test Quality Standards & Flakiness Prevention

# Purpose
This document defines the quality bar, structural patterns, and readability requirements for test code. High-quality tests serve as living, executable documentation for the system while maintaining 100% determinism.

# Scope
Applies to all automated test files written by engineers or generated by AI coding agents.

# Quality Standards

## 1. The AAA (Arrange-Act-Assert) Structural Pattern
Every test method MUST clearly separate its lifecycle into three distinct phases:

```
// 1. Arrange: Setup the specific test context and preconditions
user = UserFactory.create(tier: 'gold');
cart = CartFactory.create(items_count: 5, subtotal: 100.00);

// 2. Act: Execute the single method or endpoint under test
result = discountService.applyDiscount(cart, user);

// 3. Assert: Verify the exact expected outcome and side effects
expect(result.final_total).toBe(85.00);
expect(result.discount_amount).toBe(15.00);
```

## 2. Expressive, Sentence-Like Test Names
- Test names MUST clearly describe:
  1. The scenario or input condition.
  2. The specific action being performed.
  3. The expected result.
- **Good Examples:**
  - `it('calculates 15% discount for gold tier customers with orders over $100')`
  - `test('rejects checkout when requested quantity exceeds available stock')`
  - `it('throws InvalidCouponException when expired coupon code is applied')`
- **Bad Examples:**
  - `test('testDiscount')`
  - `it('works correctly')`
  - `test('test1')`

## 3. Determinism & Eliminating Flaky Tests
A test is flaky if it occasionally fails without any code changes. Flakiness destroys trust in the test suite and is STRICTLY PROHIBITED.

### Key Rules for Flakiness Prevention:
1. **Clock Freezing:** Any test relying on time, dates, expirations, or recurring schedules MUST freeze the system clock (e.g., `clock.setTestNow()`, `vi.setSystemTime()`, `freezegun`). Never rely on the live machine clock.
2. **Deterministic Randomness:** If generating random test data with Faker, ensure seeds are fixed or assertions verify structural invariants rather than exact random strings.
3. **No Thread Race Conditions:** Never use arbitrary `sleep(2)` to wait for async jobs. Use proper polling waiters, event listeners, or synchronous test job queues.

## 4. Proper Mocking Boundaries
- **MOCK EXTERNAL I/O ONLY:** Mock third-party APIs (Stripe, Twilio, SendGrid), external message brokers, or hardware interfaces.
- **DO NOT MOCK YOUR OWN DOMAIN:** Avoid mocking internal domain entities, Value Objects, or simple utility classes. If you mock everything, your tests verify mock configurations rather than actual system behavior.
- **Verify Mock Interactions:** When mocking, assert that the expected method was called with the exact expected payload.

## 5. Single Logical Concept Per Test
- A test should focus on verifying ONE logical behavior.
- While a test may have multiple assertions, all assertions in a single test method must evaluate the outcome of the same single operation.
- Do not chain 10 sequential, unrelated business actions inside a single 200-line test method.

# Verification
1. Verify that all tests follow the AAA structure with clear visual separation.
2. Confirm all tests have descriptive, intention-revealing names.
3. Verify that all time-sensitive tests freeze the system clock.
4. Verify that mocking is restricted to external I/O boundaries.
